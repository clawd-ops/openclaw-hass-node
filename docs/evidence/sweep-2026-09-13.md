## Mutation surface -- 2026-09-13

Exercised after the read-only passes above, each step authorized individually. Target
for filesystem work was `/share`, an allowed root Home Assistant does not parse as
configuration. The control-group work was run with the operator physically present.

**Provenance:** node `hass`, add-on `2026.9.13b1`, HA core `2026.9.1`, Supervisor
`2026.09.0`, HAOS `17.1`. Method was `nodes action=invoke` from the main session.

### `fs.*` -- PASS

| Command | Result |
|---|---|
| `fs.write` | 39 B created with `proposal_id: "direct"`, then updated to 57 B with v1 archived |
| `fs.patch` | `hunks_applied: 1`, content confirmed by read-back |
| `fs.move` | `history_moved: true`, source gone, `prev_sha256` chain intact |
| `fs.delete` | `trashed_to: /share/openclaw-trash/<name>.<hash>.<ts>`; original `exists: false`, trash copy `exists: true` at 39 B |

`fs.delete` trashes rather than erases. `fs.restore` on the deleted path recreated the
file and purged the trash copy (`trash_purged: 1`), and `fs.history` survived the
deletion with the chain readable.

`/share` is an unprotected root, so direct writes succeed without a proposal bridge.

### `fs.restore` -- FAIL

`fs.restore` is 1-based while `fs.history` returns a 0-based array.

| Requested `version` | Entry returned |
|---|---|
| `0` | entry 0, silently clamped rather than rejected |
| `1` | entry 0 |
| `4` | entry 3 |

A caller asking for a specific version silently receives a different one. Data-integrity
class rather than cosmetic. Related: `fs.diff` keys off a sha256 string, `fs.restore`
off an integer index, and `fs.history` emits neither.

### Add-on lifecycle (Tier B) -- PASS, with one misreport

`ha.addon_start` and `ha.addon_stop` both succeeded, with the resulting state confirmed
independently. This supersedes the earlier `refused-as-designed` reading, which came
from a stale July gateway plugin build rather than from node behaviour.

`ha.addon_restart` **FAIL**: returned `INVALID_REQUEST` on a client timeout for a restart
that had actually completed. The operation succeeded and the caller was told it failed.

### HA control group -- PASS

| Command | Result |
|---|---|
| `ha.call_service` | `persistent_notification.create` succeeded, notification visible in HA |
| `ha.light_turn_on` | `light.group_master_bedroom` off to on, brightness 255, 5000K |
| `ha.light_turn_off` | returned to the captured baseline exactly, all attributes `null` |

Input validation is good on this path: `ha.call_service` rejected an unknown top-level
parameter and an unknown domain, and `ha.light_turn_on` with no target enumerated every
valid targeting option.

An initial member-level light test read as `partial`. That was a Zigbee2MQTT/Hue bridge
grouping property of this install, not node behaviour: the bridge applies a command to the
whole bound group while HA updates only the addressed entity. Re-run at group level, both
commands behave correctly and report accurately.

`changed_states` was empty on every mutating call while the device physically changed.
The field exists, is always `[]`, and gives a caller no way to see the actual blast radius.

### `ha.reload_config` -- REFUSED

```
ha.reload_config denied: adminToken is not configured for this node | INVALID_REQUEST
```

`ha.check_config` returned valid immediately before, so the refusal is the gate and not a
configuration problem. The shipped plugin's `enforceAdminOp` checks `policy.adminToken`,
while `docs/design/COMMAND-TIERS.md:88` states that no add-on admin token exists and that
the model is `allowAdminOps` plus a resolved permission request. Docs and shipped code
describe different authorization models. Affects `ha.reload_config` and `ha.update_install`.

The gate short-circuits before parameter validation, so the documented domain-rejection
path could not be exercised.

### Mutation authorization gate -- REFUSED AS DESIGNED

Target chosen for minimum blast radius: `ha.config.area_registry` `create`, since areas are
inert metadata.

| Probe | Result |
|---|---|
| `create`, no `proposal_id` | `PROPOSAL_REQUIRED` |
| `create`, `proposal_id: "direct"` | `PROPOSAL_REQUIRED` |
| `create`, `proposal_id: "bogus-not-a-real-proposal"` | `PROPOSAL_REQUIRED` |

The third is the exact case `docs/VERIFICATION-2026-09-11.md` section 0 recorded as a
critical `CODE-FAIL`, claiming `_require_proposal` would accept any non-empty string other
than `"direct"`. It refuses. That finding is fixed at this head.

The refusal states the rule rather than only the rejection:

```
PROPOSAL_REQUIRED: ha.config.area_registry action=create: mutation unavailable
until a trusted approval verifier is implemented; proposal_id alone is not
authorization
```

The same refusal and message appeared across three command families
(`ha.config.area_registry create`, `ha.config.helpers create`, `ha.config.scene save`).
Area count was unchanged at 27 before and after; nothing was created anywhere.

**Only those three actions are recorded as live.** The remaining 16 mutating
`ha.config.*` actions are covered by the same uniform gate by inference, not by
observation, and the ledger's conflict rule holds that live evidence outranks repo
inference rather than substituting for it.
